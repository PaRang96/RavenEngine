The decisions depend on each other, and under the no-throwaway rule the order matters more than any single answer:

- The **layout** (FD-17) decides where M6-7 moves the sample components, so it comes first.
- The **field table** (FD-08) feeds the file format, unknown data, renames, migration and prefabs.
- **Identity** (FD-09) feeds the hierarchy, the file format, Commands and prefabs.
- The **error rule** (FD-06) is applied by every step, so it is written down before the first one.

None. The 2D Courtyard run is scheduled at M6-7, because Courtyard's movement moves into a game system there (FD-12). The public `TryNormalMatrix` stays public (FD-06).

## Goals and fixed constraints

- **M6A exit (roadmap):** a game defines a component the host never compiles, authors it in a scene file, and edits one of its fields while running, with no restart. The save/load round trip runs in CI. Spawning and despawning 1k entities per frame among 100k stays within budget. This is the stable contract M4 ports against.
- **Joint ECS and hot-reload goal:** retained state stays plain component bytes owned by the host. Nothing retained may point into a game module.
- **No throwaway work:** no step may write code that a later M6 step replaces.
- **Minimal tests:** add a tracked test only to guard behavior that an upcoming change rewrites ([section](#tracked-tests)).
- **Minimum spec:** every budget is measured on the RTX 3070 Ti laptop, in Release.
- **Future editor:** v1 has no editor, but ownership must allow editor and play sessions later.
- **Public API:** stays independent of OS headers. macOS and Linux follow through the platform interfaces.

## How the decisions serve the v1 goals

| Decision | Cross-platform | ECS | Hot reload | Performance | Future editor |
| --- | --- | --- | --- | --- | --- |

| FD-08 field table | Same table on every compiler | Base of generic tools | Base of field migration | — | Inspector fields come from it |

| FD-13 worlds | — | Isolation by construction | — | No per-view world filter | A play session is a second world |
| FD-14 Commands | — | Structural changes at fixed points | — | Batched index updates | Undo can record the same commands |

## FD-17 — Game project layout, and the module contract

### Terms

- **Game root:** a folder with one game's code, content and project file.
- **Module contract:** a hash the host compares before it loads a game DLL. If it differs, the host refuses the DLL and you must rebuild and restart the host.

### Today (checked)

- One game module lives inside the engine's private tree. [Private/Game](../RavenEngine/Private/Game) holds `RavenGame.cpp`, `InteractionGame.cpp/.hpp` and `GameComponents.hpp` (the 2D `Velocity`).
- The sample host code is compiled into `RavenEngine.exe`: about 1,400 lines in [Private/Samples](../RavenEngine/Private/Samples). That code includes private engine headers:
  - `PerspectiveLevel.cpp:2` includes `Assets/AssetPath.hpp`.
  - `PerspectiveSample.cpp:2` includes `Core/FrameTrace.hpp`.
  - `OrthographicLevel.cpp:5` includes the game module's `Game/GameComponents.hpp`.
- Sample components are public engine headers: [InteractionComponents.hpp](../RavenEngine/Public/Raven/Components/InteractionComponents.hpp) defines Switch, Rotator, Door, Goal, Pickup and Attempt in `Raven::ECS`.
- The contract ([GameContract.cmake:5-16](../cmake/GameContract.cmake)) hashes every `.hpp`, `.cmake` and `.in` file under `RavenEngine/Public`, `RavenEngine/Private/Game` and `cmake/`, plus the root and engine `CMakeLists.txt`, `CMakePresets.json` and the game `CMakeLists.txt`. Any edit to one of those forces a host restart.
- The game folder is hard-coded in four places:
  - `GameModule.cpp:100` and `GameModule.cpp:123` (the watch lists),
  - `GameContract.cmake:6-9`,
  - `RavenGameSources.cmake:3-4`.
- All content lives in one root, `Content/`, with one `Project.ravenproject`.

### Layout options

| Option | Strength | Cost |
| --- | --- | --- |
| (a) Keep one in-tree game under `Private/Game` | No restructuring. The reload loop, scripts and docs stay as they are. | Three clients (the 3D game, the stress sample, the 2D sample) share one module and one content root. "Only engine APIs" cannot be proved while the samples sit in the engine's private tree and include private headers. The host keeps compiling sample components, which blocks migration (H6). |
| (b) Game roots under `Games/`, outside the engine tree. Each root has its module source, content and project file, and is built against the engine by source path. One generic engine host runs a root. | The compiler proves the public API is enough: a game root sees only `RavenEngine/Public`. The host compiles no game components, which migration needs. It gives M7's "clone, build, modify and package a game" a real shape. | The game build, the contract and the watch lists are restructured. The host needs a way to select a root. Each root copies the few shared content files it uses. |
| (c) The engine as an installed SDK package | The cleanest separation, and the usual shape for a released engine. | Install rules, versioning and a package layout with no v1 user. |

### Sub-decision: what remains of the sample host code

Once the engine owns the frame pipeline (M6-1) and the generic scene format exists (M6-6), the sample clients have almost nothing left that a game module cannot do:

| Option | Strength | Cost |
| --- | --- | --- |
| (i) One generic engine host. All game behavior is in the game module's systems; engine developer keys (F5 reload, F7 views, scene switching) stay engine features. `ApplicationClient` leaves the public API. | All gameplay reloads. A player build is the same host plus a module. Nothing sample-specific stays in the engine. | Camera control (free-fly, orbit) and the 2D movement must move into game systems. The 2D part needs the 2D run. |
| (ii) Each root also has a host-side client linked into its own executable | Host-side code can hold any C++ state. | Host-side game code does not reload, and it can include anything, so "only engine APIs" is again unchecked. Two kinds of game code to document. |

### Contract options (once migration exists)

| Option | Strength | Cost |
| --- | --- | --- |
| (i) Keep hashing the whole tree | Simple and safe. | Every game header edit restarts the host, so field migration is never reached and the M6A exit cannot be met. |
| (ii) Hash only the engine's public surface: engine public headers, the engine CMake that sets game compile flags, and the toolchain. Game components are checked by the field table at activation. | Game header edits reload. An engine ABI change still restarts. The input list is generated once by CMake, which replaces the four hard-coded lists. | The engine's public surface must be listed precisely. |
| (iii) Check component layouts only | Fewest restarts. | A change to a non-component engine type (for example `InputState`) goes unnoticed and corrupts memory. |

### Recommendation: (b) with host (i) and contract (ii)

- **Roots:** `Games/Samples/` holds today's 3D samples (Perspective, Gallery, Assemblies, Puzzle, Collection) and the stress scenes. `Games/Courtyard/` holds the 2D sample. The M6C sample game gets its own root when it starts. Each root holds:
  - `Project.ravenproject` and its `Content/`,
  - `Source/` for the module, with its components and systems,
  - a small `CMakeLists.txt` that calls one engine function, for example `raven_add_game(<name>)`.
- **Host:** `RavenEngine.exe --game <root>` runs a root. CMake records a default root, so launching from Visual Studio or VS Code still works without options. The player build packages one root.
- **Contract:** (ii). CMake writes one generated file with the contract inputs and the root's watched folders. The contract function, the build and `GameModule` all read that file.
- **Sample generators:** `create-puzzle`, `create-collection` and `create-benchmark` in `RavenSceneTool` are sample code. They move into the Samples root as a small tool target.
- **How this absorbs the other options' strengths:**
  - From (a): the reload loop stays the same child build. Only its source folder becomes a parameter.
  - From (c): the root depends on the engine only through public headers and one CMake function, so it could turn into a package later without changing game code.

**Lands:** the layout and host at M6-7; the narrowed contract right after M6-7 and before M6-8, because migration needs it.

**Effect on goals:** goals 2 and 3 directly. It is also the precondition for H6 migration.

## FD-06 — What a host stage does with bad data

### Today (checked)

The pre-M6 fixes already follow a tiered rule, but only case by case:

- A zero-scale lit object is hidden (`RenderWorld.cpp`, `TryNormalMatrix`).
- A bad texture reference samples white (`Scene::TryUseAsset`), and a bad sprite texture is skipped.
- A missing ancestor makes a detached root, logged once per entity.
- A throwing registration is reported and the old module stays active.

The host frame itself has no boundary. `Application.cpp:111-146` calls `PrepareFrame`, the systems and `OnFrame` directly, and an exception from a host stage outside the systems still ends the session.

### Options

| Option | Strength | Cost |
| --- | --- | --- |
| (a) Throw everywhere, and catch at one frame boundary | Smallest code at each site. | A throw half-way through a stage leaves derived state half-written, so the boundary must rebuild everything. It also hides which object was wrong. |
| (b) Tiered: bad data gives a placeholder or a hidden object plus one log line; API misuse throws to the caller; out-of-memory and broken invariants end the process | The session survives a gameplay mistake, and the mistake stays visible. Engine bugs are not masked. | Each stage needs a defined placeholder. |
| (c) No exceptions in engine code: result codes everywhere | Predictable control flow, and nothing unwinds across the module boundary. | A rewrite of authoring and IO code that works today, with no v1 goal behind it. |

### Recommendation: (b), written as the engine rule

| Tier | What counts | What happens |
| --- | --- | --- |
| Data error | A value written by game code or a file that the engine cannot use: an invalid transform, a missing asset, an unknown reference, a component section that does not match | A defined placeholder (hidden object, white texture, detached root, skipped element). One log line per object and cause, repeated only after the value changes. |
| API misuse | A call the API forbids: a structural change inside a view, a foreign entity, a write to a host-owned component | The call throws (`std::logic_error` family) to its caller. Inside a system, the system boundary suspends that system, as M5 does today. |
| Fatal | `std::bad_alloc`, a broken engine invariant (an internal assert) | Log and end the process. Continuing would hide corruption. |

- **Frame boundary (M6-1):** an exception that reaches a host stage anyway is logged once. That stage's derived state is reset; for example, the render world rebuilds on the next `Sync`. The frame is skipped, and the session continues.
- **Already applied:** ARCH-RT-01 to RT-04 use exactly these placeholders, so nothing that landed is replaced.
- **Sub-decision on `TryNormalMatrix`:** FutureDecisions recommended keeping it private. It landed public in `ae4423a`, so that `NormalMatrix` throws on top of one shared copy of the math for authored data. Making it private later costs one host restart. **Recommend keeping it public.**

**Effect on goals:** goal 3 (recovery). It costs nothing per frame, because nothing throws in the normal case.

## FD-08 — The field table

### Terms

The **field table** is a runtime list of each component's fields: name, offset, size and type. Serialization, migration, prefabs, saves and a future inspector all read it.

### Today (checked)

- `RAVEN_COMPONENT(Type, Fields...)` ([Component.hpp:185-191](../RavenEngine/Public/Raven/ECS/Component.hpp)) already stores the field names as one string (`FieldNames = #__VA_ARGS__`). It also returns references to every field, and checks at compile time that every member is listed in order.
- `LayoutHash` hashes the type name, field names, size and the laid-out sizes. It does not see a field's type, so changing an `int32` to a `float` keeps the hash (ARCH-ECS-02).
- No runtime table exists. The module table registers only systems (`RavenRegisterSystems`, [GameSystems.hpp](../RavenEngine/Public/Raven/Core/GameSystems.hpp)).

### Options

| Option | Strength | Cost |
| --- | --- | --- |
| (a) The existing macro emits the table, registered through the module table | No new tool and no change to any component declaration. It cannot drift from the struct, because the macro already checks every field. | Macros see only names and types. Per-field metadata (ranges, display names, "do not save") needs an extra macro form later. |
| (b) Hand-written registration functions | Any metadata can be attached. | A second description of each struct, which can drift from it. More work per component. |
| (c) An external code generator that parses headers | Rich metadata and attributes; large engines work this way. | A parser to maintain on three platforms, and an extra step inside the 1.5 s reload loop. |
| (d) Wait for C++26 static reflection | The cleanest long-term source. | Not usable on the project's compilers today, so M6 cannot depend on it. |

Registration route:

| Option | Strength | Cost |
| --- | --- | --- |
| Through the existing table (`table.Component<T>()` in `RavenRegisterSystems`) | One entry point, one contract change. | The table name now covers more than systems. |
| A separate `RavenRegisterComponents` export | Each export does one job. | A second entry point to look up, version and keep in step. |

### Recommendation: (a), registered through the existing table

- **Per field:** name, offset, size and a type tag. The tag is a scalar kind, an engine value (`Vec3`, `Vec4`, `Mat4`, `AssetRef<Kind>`, `EntityRef`) or a fixed array of one of those with its count. Names and types come from the macro; offsets are measured once at registration from a value-initialized object.
- **Type tags go into `LayoutHash`**, so a type change is detected. A compile-time `static_assert` on the hash guards this ([tests](#tracked-tests)).
- **Defaults** are captured as bytes from a value-initialized `T{}` at registration. They are used for new fields in migration and for fields that are missing from a file.
- **Host copy:** the host copies the table by value, including the strings, so nothing points into the module after it unloads.
- **Engine components** register in RavenCore through the same function.
- **Later metadata:** the record keeps a flags field, so a later macro form (for example "do not save") fills it without a format change.
- **Metadata stays out of the layout hash** *(added at decision time, for expandability)*: display names, ranges and other editor hints go in a separate list of attributes keyed by field name. Adding one later never changes `LayoutHash`, so it never triggers a migration or a contract mismatch. Only what changes the bytes (names, types, sizes, order) goes into the hash.

**Effect on goals:** goals 2 and 3. It is the base of FD-10, FD-11, FD-15, FD-16 and H6.

## FD-09 — Persistent entity identity

### Today (checked)

- An `Entity` is a runtime handle: registry ID, index and generation ([Entity.hpp](../RavenEngine/Public/Raven/ECS/Entity.hpp)). The registry ID comes from a per-process counter (`Registry.cpp:22`), so a handle means nothing in a file or in another run.
- Entities are found by authored name through `std::map<std::string, Entity> m_Names` (`Scene.hpp:89`).
- Components refer to other entities by name. `SceneReference` is a 129-byte character array (`InteractionComponents.hpp:12`), and `DoorComponent` holds four of them, 516 bytes.
- `StaticMeshComponent` stores a runtime `MeshHandle` (`StaticMeshComponent.hpp:12`), which cannot be saved.

### Options

| Option | Strength | Cost |
| --- | --- | --- |
| (a) A 64-bit ID per entity in a `Scene`-owned table | 8 bytes, no extra pool, fast lookup. Enough for references inside one scene. | No cross-scene references by itself. |
| (b) A UUID component on every entity | Globally unique, so cross-scene references and prefab instances need nothing more. | 16 bytes and a pool entry per entity (100k in the stress scenes). Game code can see and overwrite it. |
| (c) Keep authored names as the identity | Readable in files, and no new concept. | A rename breaks every reference. String compares at runtime. Spawned entities need invented names. |

### Recommendation: (a), with random IDs and `EntityRef`

- **IDs:** each entity gets a random 64-bit ID from the platform random-byte hook, stored by `Scene` in two tables: ID to entity, and entity index to ID. A collision is checked on insert and redrawn; among 100k entities its chance is about 3 × 10⁻¹⁰.
- **References:** components hold `EntityRef { std::uint64_t Id; }`, an approved component value. `SceneAccess::Resolve(EntityRef)` returns the live `Entity` or null. A system may keep the resolved handle only for one update, like other borrowed data.
- **Names:** names stay as optional labels for logs, tools and `FindEntity`. They are not identity, and two entities may share one.
- **Meshes:** `StaticMeshComponent` holds `AssetRef<MeshAsset>`. The render world resolves it when it changes, so `MeshHandle` leaves components (M6-4).
- **How this absorbs (b)'s strengths:**
  - Random IDs from two scenes or two contributors do not collide. A later cross-scene reference is just the pair (scene asset ID, entity ID), with no format change.
  - A play-session copy (FD-13) keeps the same IDs, so references need no remapping. Only prefab instancing (FD-15) remaps.
- **Platform note:** the random-byte hook exists on Windows. The Linux and macOS hooks are already M4 items.

**Effect on goals:** goals 2 and 3, and the future editor (selection and undo key on the ID).

## FD-07 — How the hierarchy is stored

### Today (checked)

- Parents are a private `std::unordered_map<Entity, Entity> m_Parents` in `Scene` (`Scene.hpp:86`).
- Any create, destroy or reparent rebuilds the whole world order.
- Measured on 2026-11-24 at 100k entities ([record](ECSDesign.md#structural-change-record-2026-11-24-pre-m6)), against the 4 ms CPU frame budget:
  - Spawning 1k takes 17.6 ms.
  - Reparenting 1k takes 17.7 ms.
  - Despawning 1k takes 378 ms, because each destroy scans every parent link.
- Files store parents by name (`SceneDocument::Parents`, a `std::map<std::string, std::string>`).

### Options

| Option | Strength | Cost |
| --- | --- | --- |
| (a) Keep the `Scene` side table, add a child index | Smallest change. | The hierarchy stays invisible to generic serialization, copying and the field table, so each needs a special path. |
| (b) Parent, FirstChild and NextSibling all as components | Everything is ECS data. | Sibling links are derived data. Every reparent writes 3–5 entities, links must be repaired on each erase and copy, and redundant data is saved. |
| (c) A saved `ParentComponent` plus a runtime index in `Scene` | The saved data is minimal, and serialization and copying carry the hierarchy without special code. | A rule is needed for who may write the parent. |

Write rule for (c):

| Option | Strength | Cost |
| --- | --- | --- |
| (i) Only the host writes it, through `Scene::SetParent` (or a command) | No per-frame reconciliation. Cycles are checked at one place. | A future editor calls `SetParent` instead of a generic field write. |
| (ii) Anyone writes it, and `Scene` reconciles from change ticks each frame | Generic editor writes just work. | A scan every frame, plus cycle checks when applying. |

### Recommendation: (c) with write rule (i)

- `ParentComponent { EntityRef Parent; }` is the saved truth.
- `Scene` keeps a runtime index: a child list and depth per entity, and entities bucketed by depth for the world-transform pass. Spawn, destroy and reparent update only the entities they touch.
- **Host-owned components:** a component trait marks `ParentComponent` and `WorldTransformComponent` as host-owned. `SceneAccess`'s mutable paths (`Write`, mutable `TryGet` and views) reject them at compile time, and game code changes the parent through Commands (FD-14). This turns the rule into a compiler check instead of a convention.
- **How this absorbs (ii)'s strength:** an editor write goes through the same `SetParent` that Commands use, so there is still one path.

**Effect on goals:** goal 4 (structural changes cost what they touch) and goal 2.

## FD-10 — Scene file format and conversion

### Today (checked)

- 3D scenes use the positional binary format `RVN3DSCN` version 1 or 2 (`SceneDocument.cpp:35-37`).
- Its schema is the sample's: `SceneDocument` has fixed lists of meshes, groups, switches, rotators, doors and goals, plus `CameraId`, `ControlledMesh` and `Beacon`.
- 2D levels are text (`.ravenlevel`).
- `Content/Levels` has nine binary scenes and two 2D levels. v1 has no editor, so files and `RavenSceneTool` are the authoring interface.
- **Assessment Q8 answered by a check, not by asking:** the six tool-generated scenes (Puzzle, Collection, Benchmark-100/500/2000/4000) were regenerated into a scratch folder on 2026-11-24, and all six are byte-identical to the committed files. They were not hand-edited after generation.
- The other three binary scenes (Perspective, Gallery, Assemblies) and the two 2D levels came from hand-authored or imported text, so they must be converted, not regenerated.

### Format options

| Option | Strength | Cost |
| --- | --- | --- |
| (a) Chunked binary only | Fast and compact at 100k entities. Keeps today's 3D workflow and atomic saves. | Opaque to `git diff` and merges; every edit needs the tool or code. |
| (b) Text only | Diffable, mergeable and editable by hand, which matters while there is no editor. | Slow and large at 100k entities; float round trips need care. |
| (c) Text as the source, binary as a cooked form | Both strengths. | Two formats to keep in step, and a cook step in the reload path. |

### Conversion options

| Option | Strength | Cost |
| --- | --- | --- |
| Convert once with a tool, then delete the old readers | One reader in the engine. | A one-time conversion, checked by a probe. |
| Keep a legacy runtime decoder | No conversion step. | Sample-specific code stays in the engine forever. |

### Recommendation: (a), plus a text dump/apply command, convert-then-delete

- **File shape:** a header (magic, format version), then one section per component type. Each section carries:
  - the type name and layout hash,
  - **its own field list** (name, type tag, size),
  - the entity IDs, then the values packed field by field.
  An entity section holds IDs and labels. Scene-level settings such as the active camera and lighting become ordinary components.
- **Why the section carries its field list:** a file written with an older component layout loads through the **same name-and-type matching** that live migration uses (H6). One mechanism covers old files and live reload.
- **Text:** `RavenSceneTool dump <scene>` writes a lossless text form, and `apply` writes it back. Both are written once against the field table, so they work for every component.
- **Deterministic output** *(added at decision time, for expandability)*: the binary writer and `dump` order entities by ID and fields by field-table order, and write floats in a round-trip-exact form. Saving an unchanged scene gives identical bytes, so diffs show only real changes. If text later becomes the committed form (a second scene author, or the editor), the dump already is that form, and no new tool is needed.
- **Conversion at M6-6:**
  - The six generated scenes are regenerated by their generators.
  - The other five files (Perspective, Gallery, Assemblies and the two 2D levels) go through a one-time converter. An ignored probe checks that each converted file gives the same world as the old reader, entity by entity.
  - The old readers (`RVN3DSCN`, `.ravenlevel` and the legacy import) are then deleted.
  - The 2D levels are converted at M6-6, but they are only seen running at the 2D run at M6-7.
- **Project file:** `raven-project 2` ignores unknown lines, so later sub-asset lines (M6B) need no new version.
- **How this absorbs the text options' strengths:** reviews and hand edits go through `dump`/`apply` without a second runtime format. Revisit committing text when a second person edits scenes or the editor arrives.

**Effect on goals:** goals 2 and 3, and goal 4 for load time at 100k.

## FD-11 — Data whose component type is not registered

This happens when a game DLL fails to load, or a component was removed from the game.

### Options

| Option | Strength | Cost |
| --- | --- | --- |
| (a) Keep the section as opaque bytes, write it back unchanged, and log it | A broken DLL never destroys authored data; this matches last-good recovery. | Stale data can stay until someone removes it on purpose. |
| (b) Reject the file | No stale data. | A scene cannot load while the DLL is broken, which is exactly when hot reload must keep working. |
| (c) Drop it silently on save | Files stay clean. | Silent data loss. |

### Recommendation: (a)

- Unknown sections, and unknown fields inside a known section, are kept byte for byte and written back by every tool rewrite. One log line names each unknown type.
- Removing stale data is explicit: a `RavenSceneTool prune` command lists what it would drop and drops it only when asked.
- The running game never saves scene files in v1, so a stale section cannot be lost by gameplay. Save data is FD-33, in M6C.

## FD-16 — Renamed fields and components

### Today (checked)

- The migration design (H6) copies by matching name and type, so a rename loses the value.
- A component's `TypeId` is a hash of its full type name (`Component.hpp:188`), so renaming a component, or moving it to another namespace, also creates a new, empty pool.
- At M6-7 every sample component moves out of `Raven::ECS`, so this happens to every sample component at once.

### Options

| Option | Strength | Cost |
| --- | --- | --- |
| (a) A rename is a removal plus an addition | Nothing to build. | The value is lost in the live world and in every file. |
| (b) An alias list next to the component, read by both the file loader and migration | One small mechanism covers live reload and files. | Aliases pile up until someone removes them. |
| (c) A one-off conversion tool per rename | No runtime mechanism. | Does not help the live session; one tool run per rename. |

### Recommendation: (b), with a tool to retire aliases

- A macro form next to `RAVEN_COMPONENT` lists the old type names and old field names, for example `RAVEN_COMPONENT_ALIASES(Raven::ECS::DoorComponent, "Required=RequiredRotators")`. It goes into the field table.
- The file loader and live migration both match the current names first, then the aliases.
- `RavenSceneTool upgrade` rewrites scenes with the current names and reports which aliases are still used. An alias can then be deleted safely.
- M6-7 uses this mechanism for the namespace move. That is its first real use, so it is checked before any game depends on it.

## FD-12 — What a game system receives

### Today (checked)

- `SystemContext` ([GameSystems.hpp:26-33](../RavenEngine/Public/Raven/Core/GameSystems.hpp)) carries:
  - `GameInstance& Game`, which gives the raw `Registry`. Game code can bypass `Scene` through it (the ARCH-RT-03 route).
  - `GameBindings { Camera, Player, Mesh, World, Interactions }` ([ApplicationClient.hpp:17-25](../RavenEngine/Public/Raven/Core/ApplicationClient.hpp)).
  - `GameUpdateResult& { PlayerDisplacement }`.
- Player, Mesh and PlayerDisplacement are sample concepts, and they are part of every game DLL's ABI and the contract hash.
- The host switches gameplay off by returning empty bindings.

### Options

| Option | Strength | Cost |
| --- | --- | --- |
| (a) Engine concepts only. Player and similar become game-defined tag components; the result logic moves into systems. | The host reads only engine-defined components. New gameplay needs no public-header edit and no restart. | One planned contract break. Courtyard's movement moves into a game system and needs a 2D run. |
| (b) Generic named entity slots and an opaque result | A smaller break now. | A second identity system that serialization, copying and the editor must all carry. Authored tags would replace it later. |

How gameplay is switched off:

| Option | Strength | Cost |
| --- | --- | --- |
| A play state on the engine session; the schedule skips game phases unless playing | Matches today's behavior, and is what an editor's edit mode needs. | All or nothing: no "this system also runs while paused". |
| A mode component that each system checks | No schedule change. | Every system must remember to check it. |
| Per-system run conditions in `SystemDesc` | Fine-grained. | More schedule API than any current game needs. |

### Recommendation: (a), with the play state on the session

```cpp
struct SystemContext
{
	SceneAccess World;                    // the scene being played
	const InputState& Input;
	const FrameTime& Time;
	std::span<const PickHit> Picks;       // hits from the presented frame, delivered once
	Commands& Commands;                   // structural changes, applied at the phase end (FD-14)
};
```

- No raw `GameInstance` or `Registry`. Game code reaches components only through `SceneAccess`, which enforces scene scoping and the host-owned rule (FD-07).
- **Camera:** the camera is an ordinary entity with `CameraComponent` and a Transform, which game systems may write, for example for free-fly. The engine marks the active camera with an engine tag. There is no special camera slot.
- **Play state:** a play state on the session (playing, paused). The schedule runs game phases only while playing.
- **Later:** a per-system "runs while paused" flag is added when the first system needs one. It is a new `SystemDesc` field, not a break.
- **This is the one module-contract break of M6 (M6-7).** `GameBindings` and `GameUpdateResult` stay frozen until then.

## FD-13 — Worlds and registries

### Today (checked)

One `Registry` lives in `GameInstance`, shared by every scene, with a per-slot scene ID ([ECSDesign D8](ECSDesign.md#d8--scene-membership-in-a-shared-registry-per-slot-scene-id-step-4)). This is option (b) below, applied to a single world. `Registry.cpp:354` already rejects handles from another Registry.

### Options

| Option | Strength | Cost |
| --- | --- | --- |
| (a) One Registry per world; scene IDs separate scenes inside a world | Isolation by construction. A play session is a copy of each pool. Ticks and journals are per world. | Entities cannot be viewed across worlds in one query (rarely wanted). |
| (b) One shared Registry for every world, with scene IDs | One place for everything. | Every view, journal and tick consumer must filter by world, and a play-session bug can touch editor data. |

### Recommendation: (a)

- v1 has one world, so M6A changes nothing in code here. `GameInstance` is that world.
- The decision forbids a design: no world filter is ever added to views, journals or ticks.
- A future play session copies the pools into a second `Registry` and keeps the entity IDs (FD-09), so references keep working.

## FD-14 — Deferred structural changes (Commands)

### Today (checked)

Structural changes during a view are rejected (`Create` throws), and no sample spawns or despawns at runtime. Commands were deferred in M1 (D5) and are scheduled at M6-7.

### Options

| Option | Strength | Cost |
| --- | --- | --- |
| (a) Apply at the end of each phase | Few, fixed sync points; deterministic; leaves room for parallel systems inside a phase. | A system cannot see what an earlier system in the same phase spawned until the phase ends. |
| (b) Apply after every system | Later systems see earlier results. | Many flushes, each touching the hierarchy index; rules out parallel systems inside a phase. |
| (c) Allow direct structural calls whenever no view is open | Simplest for game code. | Behavior depends on where the call is made, and is easy to break by wrapping code in a view; rules out parallel systems. |

### Recommendation: (a), applied after each fixed step and at the end of `Update`

- **IDs at record time:** `Commands.Create()` returns an `EntityRef` with a new persistent ID (FD-09). It can be stored in components at once, and it resolves after the flush. This needs no handle reservation inside the Registry. Later commands in the same buffer may address the new entity by that ID.
- **Through Scene:** destroy, reparent and add/remove all go through `Scene`, so the hierarchy index (FD-07) and the render-world journal see every change.
- **Bad commands:** a command on an entity that is already gone is a data error (FD-06): it is skipped and logged once.

## FD-15 — Prefabs

### Options

| Option | Strength | Cost |
| --- | --- | --- |
| (a) Spawn from code only | Nothing to build. | Every spawned object is described in C++, so its values are outside asset hot reload. |
| (b) Instantiate a scene file as a template: copy it with new IDs, no overrides | Reuses the generic format, and the same copy-and-remap code that play sessions and multi-object FBX need. | Editing one instance does not flow back; no nesting rules. |
| (c) Nested prefabs with per-instance overrides | What a full editor workflow wants. | Override storage, merge rules and a large test surface, with no editor in v1 to use them. |

### Recommendation: (b), built when the sample game first needs it

- An instance copies the template's entities through Commands, with fresh IDs. References between the copied entities are remapped to the new IDs; references to anything outside are kept.
- Nothing is built in M6A. The decision only keeps the format and the IDs ready for it.

## Owner decisions

Decided on 2026-11-24. The owner delegated the choice: "Make best decision based on businesses alignment and expandability in the future". Each option was judged on two tests:

- **Alignment:** it serves the v1 goals and M7's "clone, build, modify and package a game", without work that has no v1 user.
- **Expandability:** it keeps the post-v1 directions in [FutureDecisions.md section 11](FutureDecisions.md#11-after-v1-directions-and-what-to-keep-open-now) cheap: editor and play sessions, parallel systems, streaming, physics and an SDK package.
